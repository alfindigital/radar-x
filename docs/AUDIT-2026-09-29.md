# RADAR-X: hackathon readiness audit and roast

Audit date: 29 September 2026. Baseline: local commit `3ea9334`, initially clean working tree. Standard: a credible, useful Track 3 submission capable of competing seriously, not a generic production-readiness checklist. This is an assessment and proposed plan, not a claim that winning can be guaranteed.

**Verdict:** RADAR-X has a working product shell and a substantial Sectors dataset, but it is not ready to defend its analytical claims under technical judging. The largest threat is not exhausted credits: it is presenting hindsight-selected cases, incomplete outcomes, and incomplete rankings as trustworthy intelligence.

## What this folder actually contains

RADAR-X is a Next.js 16.3.5 / React 19.2.8 / TypeScript application for researching Indonesian equity disclosures and positioning. Its intended audience is retail swing traders researching over weeks or months. It combines named-holder transaction disclosures, foreign flows, broker summaries, monthly shareholder composition, prices, and IHSG comparisons.

Architecture: `scripts/ingest.ts` calls `src/lib/sectors.ts`; normalized data lives in `data/*.json`; `scripts/compute.ts` uses `score.ts` and `cases.ts`; `db.ts` exposes a JSON store; `services.ts` supplies the pages. Seven user-facing route patterns cover the board, foreign flows, issuer dossiers, case feed/detail, holder dossiers, and methodology. There is no implemented Supabase adapter, no committed automated behavioral test suite, and no committed ingest scheduler. Recharts and Zod are installed but the inspected charts use custom SVG and ingestion uses TypeScript casts rather than runtime schemas.

The live demo is [radar-x-beta.vercel.app](https://radar-x-beta.vercel.app/), and the project repository is [alfindigital/radar-x](https://github.com/alfindigital/radar-x). Git's first local commit is 19 September 2026, inside the build period. That supports commit timing; it does not independently prove repository creation time, onboarding timing, or code originality.

### Can Arjum supplement Sectors?

**Reasonable reading: yes as supplementary data; not explicitly guaranteed by the published text.** The rules say “core source,” not “exclusive source.” The decisive test is dependency, not an invented percentage of API calls. Keep Sectors filings and derived disclosure research essential; let supplementary prices or broker observations add context. Deleting all Sectors raw data AND derivatives must disable the core report even if Arjum prices remain.

Arjum publicly documents OHLCV history and broker-summary endpoints, including date-range and limit options. See [Arjum API documentation](https://stock.arjum.com/api-docs). Its broker response is a period aggregate; it must not be relabeled as daily broker history. Access under a paid plan and redistribution of raw data are separate questions. The public pages inspected did not establish explicit redistribution rights; that is **unknown**, not a finding that use is forbidden. Avoid publishing an Arjum raw-data dump until applicable plan terms establish permission. Public rendered derived displays also need to fit those terms.

Recommended path: **ship the corrected Sectors-only snapshot first**. If time and terms permit, add one freshly written Arjum adapter for a small explicitly selected issuer set, with source/date labels and cached server-side reads. Do not integrate ZPI and Pluang as well. Three providers add reconciliation, licensing, unit, and historical-adjustment work without fixing the present core bugs.

- The product fits Track 3: it performs transformations and analysis. It does not need LLM theater to qualify.
- `npm run lint`, `npm run typecheck`, and `npm run build` passed in this audit. `gitleaks git --redact --no-banner --log-level warn .` returned exit code 0 with no findings. These checks have limited scope and do not certify analytical correctness or all deployed secrets.

## Ranked findings and repair checklist

Priority definitions: P0 = submission blocker or fundamental integrity problem; P1 = core usefulness/reliability; P2 = polish; P3 = defer. Effort S = up to half a day, M = roughly one day, L = multiple days. Estimates are planning ranges, not measured implementation durations.

### F01. Distribution candidates are hidden [P0 | S]

**Evidence:** `src/lib/services.ts:75` requests `latestScores(120)`, already sorted descending; `src/app/page.tsx` filters that truncated list. Snapshot contains 256 latest scores and 46 scores at or below -25. The top 120 contain zero such scores. The deployed distribution tab shows zero and tells users to run a compute command.

**Cost:** the product fails one of its two central screening directions. More integrations cannot recover rows filtered out by the service.

- [ ] Retrieve the complete latest cohort, filter first, sort distribution ascending, paginate last, and compute counts from the full cohort.
- [ ] Test the current 256/46 fixture behavior and a synthetic negative score outside the first 120.
- [ ] Replace developer-facing empty text with a real no-matches state.

### F02. “30-day” outcomes can be 19-day returns [P0 | M]

**Evidence:** `cases.ts:51` accepts `floor(30 * .66) = 19` elapsed days; `closeOnOrAfter` falls back to the final price even when no price reaches the target. There are 21 incomplete outcomes among 144 stored non-null 30-day values. FILM 2026-09-01 is prominently advertised as a 30-day -14.3% result although prices end 2026-09-22. LUCY 2026-08-24 also has less than 30 days to 22 September.

**Cost:** the headline demo uses a mislabeled result. Fixing visual polish first would only amplify the wrong claim.

- [ ] Require complete calendar horizons; return an explicit pending/unavailable state otherwise.
- [ ] Use shared issuer/benchmark start and end sessions for comparisons; show actual dates.
- [ ] Separate transaction-relative historical return from publication-relative observation.
- [ ] Recompute cases and rewrite video/social numbers after correction. Do not preserve headline numbers as acceptance criteria.

### F03. Case selection and score contain hindsight [P0 | L]

**Evidence:** `cases.ts:194,201` creates EXIT_AHEAD only after a decline and STEALTH_ACCUMULATION only after a rise. `caseScore` uses post-move size. Those categories are legitimate retrospective descriptions if labeled that way, but cannot demonstrate advance detection. The current product statement says “before the movement is visible.”

**Cost:** a judge can reproduce apparent success from the selection rule. It provides no evidence of prediction.

- [ ] Separate contemporaneous evidence patterns from later outcomes.
- [ ] Remove future returns from pattern membership and evidence scoring.
- [ ] Keep outcome-selected legacy examples only in an explicitly retrospective view, or replace them with neutral candidate labels.
- [ ] Include one contradictory or insufficient-data example in the demo.

### F04. Transaction dates are not information-availability dates [P0 | M]

**Evidence:** `score.ts:67` filters transaction dates without filtering `filedAt`; 1,305 of 1,513 rows have a later stored filing date. The six TOWR transactions occurred on 16 September but all stored filing timestamps are on 18 September. The timestamp semantics/time zone still require provider documentation or source verification.

**Cost:** the narrative implies the tool could know on the transaction day. A disclosure arriving later cannot create an earlier actionable signal.

- [ ] Display transaction date, source/feed publication timestamp, and snapshot retrieval status separately.
- [ ] Never invent a publication timestamp from a transaction date or a file modification time.
- [ ] For historical availability claims, use verified publication data; otherwise mark availability unknown and keep results retrospective.

### F05. Cluster definition is inconsistent [P1 | M]

**Evidence:** `cases.ts:193,196` accepts three transactions OR three holders while methodology promises three holders. 97 of 136 stored CLUSTER_PATTERN records have fewer than three distinct holders. Grouping chains each event to the previous event within 30 days, allowing a cluster to span longer; 43 stored cases of all patterns span more than 30 days. Opposite-direction rows split groups based on row order.

**Cost:** “six different people” is meaningful; one holder filing three times is a different phenomenon.

- [ ] Define separate same-holder repeated-activity and distinct-holder cluster concepts.
- [ ] Implement independent buy/sell windows with an explicit 30-calendar-day maximum span.
- [ ] Test repeated rows, ties, direction interleaving, and chained 0/29/58-day events.

### F06. Missing coverage is silently converted to neutral values [P1 | L]

**Evidence:** `rawComponents` initializes absent dimensions to zero; robust distributions include these zeros. `dataPoints` is unused and increments at most four times despite its “0–5” comment. Only 40 issuers have broker data. A singleton recomputation always returns score zero. `mad` uses 1 when MAD is zero, which is arbitrary for rupiah-scale values and can saturate sparse components.

**Cost:** a tidy score hides incomparable evidence. Apparent neutrality can mean “not measured.”

- [ ] Model component value, availability, coverage, and reason explicitly.
- [ ] Compute cohort statistics from valid observations, once per component.
- [ ] Use a documented degenerate-cohort fallback; abstain when no defensible spread exists.
- [ ] Preserve fixed published weights without inflating a single available component to 100%; show coverage separately and suppress unsupported rankings.
- [ ] Do not calculate cross-sectional scores from one issuer alone.

### F07. Labels overstate what the source proves [P1 | M]

**Evidence:** `instBrokers` is always an empty set; the supposed institutional cohort becomes foreign broker value. Total shareholder-count change is called “retail exodus,” although the field is not a retail-only count. Two highly related foreign-flow measures are presented as independent evidence. `score.ts:108` uses latest holder months without an anchor cutoff; a synthetic August 1 anchor included August 31 data.

**Cost:** the product attributes intent and investor identity not established by its inputs.

- [ ] Rename components to measured quantities: reported holder net value, foreign net flow, foreign broker net value proxy, shareholder-count change, selected foreign ownership-class shift.
- [ ] Apply anchor cutoffs and explain publication-availability limitations for monthly data.
- [ ] Document foreign-metric overlap; do not advertise the weighted heuristic as calibrated confidence.

### F08. Derived snapshots retain stale cases [P1 | M]

**Evidence:** recomputing `detectCases` in memory from current raw files produces 235 cases, versus 244 stored. Nine stored IDs are absent from the current output. `compute.ts` upserts current detections without replacing the derived collection.

**Cost:** reviewers cannot reproduce what the app shows from its own raw data.

- [ ] Write versioned derived snapshots into a new directory; validate before switching readers.
- [ ] Replace the generated collection within that new version instead of merge-upserting extinct cases.
- [ ] Keep originals for comparison; no deletion is needed.
- [ ] Hash input files, record engine version, and test deterministic recomputation excluding generation time.

### F09. Request-time API calls survive quota exhaustion [P1 | S/M]

**Evidence:** unknown dossiers trigger three upstream requests in `services.ts:107`; broad catches hide failures, and `lazy=true` may still display “live fetch.” There is no genuine 24-hour TTL. `sectors.ts` has no fetch timeout and retries all 429s, including potentially permanent quota failures. No ticker-registry validation protects the request path.

**Cost:** random searches can be slow, misleading, and costly if access returns. Read-only requests can attempt writes and singleton score updates.

- [ ] Default the hackathon runtime to immutable snapshot mode with zero upstream calls.
- [ ] Known but uncovered ticker: show an honest coverage state. Unknown ticker: friendly not-found, no API call.
- [ ] Keep ingestion an explicit CLI action with timeouts, quota/error categorization, and a budget gate if ever re-enabled.

### F10. Close-only ingestion can destroy richer OHLCV [P1 | M]

**Evidence:** `ingest.ts:318` invents zero volume and flat OHLC for close-only rows. `upsertPriceDaily` replaces the complete symbol/date row. Snapshot contains 3,665 non-IHSG zero-volume rows; this count alone does not prove all were overwritten.

**Cost:** volume anomaly calculations can consume placeholders as measurements. New Arjum data would worsen reconciliation complexity without a field-level policy.

- [ ] Represent unknown OHLCV fields as null and record field provenance.
- [ ] Merge close-only observations without overwriting existing richer fields.
- [ ] Exclude unverifiable zero-volume placeholders from volume evidence; do not guess authentic zero versus unknown.

### F11. Flow windows and streaks overstate completeness [P1 | M]

**Evidence:** `getFlowRadar` counts consecutive positive observed rows, not consecutive verified exchange sessions. September 15–18 have only 242–245 flow rows/day versus roughly 688–733 on neighboring days. A gap for a ticker can look like a continued buying streak. The dossier labels all stored insider and flow sums as 90 days without filtering them.

- [ ] Display actual date ranges, observed-session counts, and per-ticker gaps.
- [ ] Break or mark streaks unknown across a missing expected session. Distinguish absence from verified zero activity.
- [ ] Filter every advertised window by the snapshot anchor, or rename it “available history.”

### F12. UI hides evidence and loses navigation on mobile [P1 | M]

**Evidence:** stored source links are not exposed in inspected trade/case tables. Sidebar is `hidden ... md:flex` with no replacement mobile navigation. Mobile screenshot at 390×844 confirms this. The SVG flow baseline is y=280 within height=300 while negative bars can extend 52 pixels downward, clipping at the viewBox. The same positive/green score component is reused for sell-case severity. `.faint` is approximately 3.42:1 against the background, below 4.5:1 for normal small text.

- [ ] Add reachable mobile navigation and keyboard-visible focus.
- [ ] Link source documents and show both transaction/publication timing.
- [ ] Give positive and negative flow equal vertical plotting space.
- [ ] Separate directional positioning from unsigned evidence strength.
- [ ] Convert visible copy, metadata, tooltips, narrative templates, and number units to English; use B for billion, M for million, and d for days.
- [ ] Give charts a readable table/text alternative and avoid hiding the only explanation on mobile.

### F13. Documentation and submission assets are misleading [P0/P1 | S/M]

**Evidence:** old deadline; “190 outcomes”; quick start `npm run ingest` has no command and exits with usage; claims of Supabase, scheduled ingestion, lazy cache, and nontracked data conflict with source. `TECH_SPEC.md` omits the final ×33.3 scale. Existing videos are described as baked-data animations outside this repo; their actual media was not inspected. These cannot be certified as compliant recordings from documentation alone.

- [ ] Publish an English no-key quick start using `npm ci`, `npm run dev` and the bundled snapshot.
- [ ] Replace claims with generated metrics and explicit limitations; preserve historical docs as labeled history where needed.
- [ ] Capture actual app use for both videos after fixes, then verify duration and link access.
- [ ] Complete social post, correct template/tag, team names, and one-sentence English problem statement.

### F14. Reliability and workspace hygiene [P2 | S/M]

**Evidence:** `readJson` turns every read/parse error into an empty array. Writes are not atomic. Services repeatedly reread multi-megabyte files; the eight snapshot files total about 12 MB. Installed Recharts is unused in inspected source. Template SVG assets remain. Git starts clean and the allowlist keeps local secrets/build output untracked.

- [ ] Distinguish corrupt required data from a legitimate empty dataset.
- [ ] Cache immutable parsed snapshots and indexes server-side; never put whole evidence JSON in client payloads.
- [ ] Make CLI publication of derived data atomic and fail validation before activation.
- [ ] Add targeted unit and workflow tests plus CI; do not build a giant platform test suite.
- [ ] Defer dependency/template cleanup until correctness is done; obtain user permission before deletion.

## Deep roast

The current UI looks more certain than its data deserves. It can hide every distribution candidate, call a single holder a crowd, score cases partly because the future already happened, and still announce that all checks are green.

The costliest mistake would be spending the remaining days adding Arjum, an LLM, and more panels while the current examples remain analytically wrong. The competitive asset is the evidence already collected; the lost opportunity is failing to make that evidence traceable and honest.

**STOP:** claiming advance detection from outcome-selected cases; calling partial returns 30-day results; treating missing data as neutral; treating foreign brokers as proven institutional owners; calling a failed fetch live; polishing simulated videos before the real workflow is corrected; running ingest merely because the README suggests it.

## Immediate top five actions

1. Fix complete-cohort filtering so the 46 existing distribution candidates become discoverable.
2. Correct full-horizon outcomes and separate contemporaneous patterns from retrospective labels; invalidate the old FILM/LUCY video claims.
3. Make snapshot mode explicit, add publication/source/coverage evidence, and disable request-time provider calls.
4. Rebuild deterministic derived snapshots and finish the English, mobile, source-linked research workflow.
5. Record the real product, complete submission materials, verify eligibility and freeze only after the final acceptance checks.
